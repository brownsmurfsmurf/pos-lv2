# テスト仕様書 v2: 簡易POSアプリ（Lv1 + Lv2）

ステップ 3 のやり直し版。`要件定義書_v2.md`（要件 70 件）、`設計仕様書_v2.md`、決定ログ（D-000〜D-010）をもとに作成。

## 読み方

- **期待値の出どころ**を、すべてのテストに付ける
  - **人**: あなたが自分で計算した期待値（E-1〜E-3）
  - **要件**: 要件の文にそのまま書いてある結果（例: 数量 0 は不可）
  - **設計**: 設計仕様書の決めごとから機械的に決まる結果（例: 14 桁の商品コードは 400）
  - **AI 算出**: 設計の計算規則に AI が数字を当てはめて出した金額。**人の検算はまだ**。金額の期待値は人が決めるのが原則なので、検算するまでは仮の値として扱う
  - **未決**: 期待値が決まっていない。自動テストにしない（いまは該当なし）
- **★**: 設計の仮の値に依存するテスト。確認事項（K-n）の答えが変われば期待値も変わる
- 根拠の欄は、確かめる対象（要件番号、決定ログ、課題の指定項目）

## 1. V 字モデル（何を、どのテストで確かめるか）

決めた順（要求 → 要件 → 設計 → 実装）の逆順に、同じ高さのものどうしを確かめる。

| 決めたこと | 確かめるテスト | 番号 | やり方 |
|---|---|---|---|
| 要求（Lv1・Lv2 要求一覧） | ユーザーテスト | UAT-01〜07、CHK-01〜06 | 実機のカメラとバーコードで人が操作する。構成は設定を目で確認する |
| 要件（要件定義書 v2 の FR / N） | 機能テスト | ST-01〜18 | 画面から DB まで通して、要件 1 つずつ確かめる |
| 設計（設計仕様書 v2 の API / DB / BFF） | 結合テスト | IT-01〜33 | API を実際に呼び、DB の中身と BFF の動きを確かめる。pytest（TestClient）、Jest |
| 実装（関数・部品） | 単体テスト | UT-B-01〜41（pytest）、UT-F-01〜31（Jest） | 関数 1 つ、部品 1 つを単独で確かめる |

テストは下（単体）から順に行う。上のテストで見つかった不具合は、原因のある工程（設計か要件か）に戻して直す。

**合格の基準**（あなたが決めたこと）: 単体テストは全件合格。

## 2. 人が決めた期待値

設計の計算規則（単価 × 数量 → 値引き → 小計の合計 → 税は合計に 1 回・切り捨て。税率 10%）で、あなたが計算した値。

| # | 条件 | 税抜合計 | 消費税 | 税込合計 | 状態 |
|---|---|---|---|---|---|
| E-1 | 150 円の商品を 2 個。会員。20% 引き | 240 | 24 | 264 | 確定 |
| E-2 | 188 円の商品を 1 個（値引きなし）と、150 円の商品を 2 個（この商品が 20% 引き）。会員 | 428 | 42 | 470 | 確定。最初の計算は 450／45／495 だった。出題文があいまいで、20% 引きを 188 円の商品に付けて計算していた。20% 引きは 150 円の商品に付くと決めて計算し直した（188 + 240 = 428、税 42.8 → 42） |
| E-3 | 240 円の商品を 1 個。会員。値引きの期間は昨日で終了 | 240 | 24 | 264 | 確定 |

E-1 は UT-B-01 と IT-13、E-2 は UT-B-02 と IT-15、E-3 は UT-B-03 と IT-14 で使う。

3 つとも、設計の仮の値（単価は税抜 K-11、税は合計に 1 回・切り捨て K-12、値引き後に課税 K-13）を前提にした数字。確認事項の答えが変われば計算し直す。
